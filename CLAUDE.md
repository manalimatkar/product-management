# CLAUDE.md

Context for Claude Code working in this repository. Read this before making changes.

## What this repository is

`product-management` is a **product-management and governance framework**, not application code. It defines the process by which product intent (design source material) becomes governed, traceable business scope, and then governed technical work -- via a Business Agent, a Business Owner approval gate, a Technical Agent, and an Architect approval gate -- before anything reaches an engineering repository. See [README.md](README.md) and [PRD.md](PRD.md) for the full picture; [PRD.md](PRD.md) section 5 has the end-to-end workflow diagram.

The repository is intentionally domain-agnostic (PRD.md, FRAMEWORK-CONFIGURATION-SPEC.md) -- it's built to apply beyond UI/design-led products, not just to software features with screens.

## Core pipeline (memorize this shape)

```
Source Material -> Design Handoff Bundle (optional) -> Design Analysis
  -> Business Requirements (Epic + Stories + Acceptance Criteria)
  -> Business PR -> Business Owner Approval -> Merge
  -> Technical Agent -> Canonical Task / Spike -> Architect Approval
  -> Technical Ready -> Developer Agent -> Implementation PR (engineering repo)
```

Two hard human gates: **Business Owner approval** (authorizes technical analysis) and **Architect approval** (authorizes development). Both are meant to be structurally enforced, not left to agent discipline.

## The pattern this repo has been built with

When asked to add or check something in this repo:

1. **Grep the whole repo first.** Things are frequently already partially covered, scattered across two or three documents. Report precisely what exists (with section citations) and what's actually missing before writing anything new.
2. **Build only the missing piece**, as a document that cites existing specs rather than duplicating their content. If a new doc restates a rule from another doc, link to the source section instead of copying it, and note which one is authoritative if they ever conflict.
3. **Resolve genuinely undefined edge cases explicitly**, with stated rationale, rather than leaving a new placeholder -- but flag each one as a default that can be overridden, not settled law.
4. **Cross-link everything.** A new document gets added to README.md's Documents list, and every existing document it relates to gets a short one-line pointer back to it (light-touch edits, not rewrites).
5. **Naming convention**: `ALL-CAPS-WITH-DASHES.md`, ending in `-SPEC` (rules), `-TEMPLATE` (fillable format), `-MODEL` or a descriptive name for cross-cutting docs.

## Git workflow (established, don't relitigate)

- **Never commit directly to `main`.** Every change gets its own branch, committed there; `main` only moves by merge (PR or Manali merging locally), never by a direct commit. Decided 2026-09-03.
- This isn't a new discipline invented for git -- it mirrors the pipeline this repository's own content governs: nothing here reaches an approved state without going through a reviewed PR (BUSINESS-PR-SPEC.md). The repository's own git hygiene now follows the same rule it prescribes for its subject matter.
- Two early commits (`7518fc1`, `d57e880`) landed directly on `main` before this rule existed, and Manali pushed them herself -- the rule applies going forward, not retroactively to those.
- Branch naming isn't formally fixed -- used so far: `docs/<short-description>` for documentation-only changes. Revisit if/when engineering-style prefixes (`feature/`, `fix/`) are needed.
- **Bridge limitation discovered 2026-09-03**: from this session's device-bridge shell, `git checkout <existing-branch>` fails whenever a tracked file's content actually differs between the current working tree and the target -- the FUSE mount blocks the unlink git needs to replace it (`error: unable to unlink old '<file>': Operation not permitted`), leaving a mixed index/working-tree state (recoverable with `git reset HEAD`, not `git reset --hard`, since that also needs to touch files). Creating a *new* branch at the current commit (`git checkout -b <name>`) is unaffected -- no file content changes. Practical effect: from this bridge, start each new branch from wherever HEAD currently sits rather than trying to switch back to `main` first; if a genuine return to `main`'s exact tracked state is needed mid-session, it likely won't succeed here -- that step waits for Manali's own terminal (or local Claude Code) instead, same as any git push.
- **Second long-lived branch, `design`, added 2026-09-03** (see open item 15) -- a raw landing zone for native Claude Design exports, deliberately separate from `main`. It follows the same "never commit directly" discipline (upload via short-lived branch + PR into `design`, reviewed by `ROLE-004`), but is not itself a feature branch merged into `main` -- it exists in parallel, permanently. `main`'s branch-first rule above is unchanged and still governs every other change, including this framework's own doc/spec edits.
- **Integration branch for agent-development work, `agents/development`, created 2026-09-10.** Unlike `design`, this is not permanent -- it's a scoped, temporary container for the whole batch of "next agent changes" (Technical Agent and Developer Agent definitions, the `run-gate-checks` and `resolve-review-decisions` skills, and anything else continuing item 19 below), so they can be tested together before any of it reaches `main`. Work lands as direct commits on this branch (mirroring how `framework/business-agent-definition` itself accumulated several commits before merging) rather than each piece getting its own branch into `main`. It merges to `main` as one PR, once the accumulated work has actually been exercised for real -- not the moment each piece is written. Superseded 2026-09-10 by `agents` (same spirit, fresh branch, for the agent-framework redefinition effort) -- `agents/development` itself was never pushed. Unrelated framework work still gets its own ordinary branch off `main`, same as always -- this is scoped to agent/skill implementation specifically, not a blanket change to the one-branch-per-change discipline above.
- **PR-authorization split into two tracks, decided 2026-09-24, since git is now used for both.** Manali: "the process is agent based" -- the git workflow around the framework's own changes should reflect that.
  - **Agent changes** (this framework's own specs/templates/.claude/.github/registries/scripts -- the pipeline's tooling and definitions, on the `agents` branch): the agent may `git commit`, `git push`, and open a PR against `agents` on its own initiative, without asking first each time. The human gate moves downstream to PR review -- Manali approves (or requests changes on) the PR before it merges into `agents`; the agent still never merges its own PR.
  - **Product changes** (Design Analysis, Business Requirements, Business PR, and other artifacts produced by actually running the pipeline against a real source, e.g. `pdf-workflow`): **updated 2026-09-24, same day.** The original reason for gating push/PR-open (no way to review a change except raw markdown on GitHub's diff view) no longer holds for anything the docs site actually renders -- a Design Analysis, a registry, a Journey/Capability/Business Rule record. `preview-docs-site.yml` already builds a live rendered preview on every PR into `main`, and an in-preview commenting widget (new the same day, `.github/scripts/docs-assets/comment-widget.js`) lets a reviewer leave real inline PR review comments straight from that preview. Review now happens on the pushed, visible artifact itself, not before it exists -- so for this content, the agent may `git commit`, `git push`, and open a PR against `main` without asking first each time, same shape as the agent-change track above; the human gate moves to PR-approval-before-merge. Artifacts the docs site does not yet render (Business Requirements, Business PR -- no preview built for either) stay under the old rule: commit locally and stop, wait for a separate explicit go-ahead before `git push`, and another, separate explicit go-ahead before opening a PR.
- **Hold a PR open until the artifact is genuinely complete; merge once, not incrementally.** Decided 2026-09-08/09, after `DA-003` (the Mapping Report Design Analysis) went through three separate merged PRs (#17 draft, #22 a narrowing fix, #23 a full reformat) and left `main`'s history as a trail of patches instead of one clean landing point. One branch, one PR per artifact or change; every review round -- comments answered, Decisions resolved, reformatting, scope fixes -- becomes another commit on that same branch/PR, never a follow-up PR. Passing CI/gate checks, or addressing one round of feedback, is not by itself a reason to merge -- merge is a distinct, later decision, made once every requirement/decision is addressed and the artifact's own Status field reads Approved (or, for a framework change, once Manali confirms it's done). Applies to both tracks above -- who is allowed to push or open the PR differs by track; when it is allowed to merge does not.
- **Git safety, non-negotiable, applies to any agent or session working this repo regardless of which model is driving.** Never run `git clean`, `git clean -fd`/`-fdx`, or `git reset --hard`. Never discard uncommitted changes, delete untracked files, or assume an untracked file is disposable -- if something unfamiliar shows up (a stray branch, an unexpected file), investigate before touching it; it may be someone else's in-progress work. Never force-push. Ask for explicit authorization before any destructive git operation, and run `git status` first whenever a command could discard uncommitted work. Made canonical here 2026-09-24, moved out of a Claude-specific personal config where it previously lived only for one model, on one machine, to see -- see the portability task list (CLAUDE.md item 22, below).
