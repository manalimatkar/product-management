# Canonical Task and Spike Templates

Reusable formats implementing [CANONICAL-TASK-SPEC.md](../specs/CANONICAL-TASK-SPEC.md). Per [PRD.md](../PRD.md) section 7.6, these are intended as GitHub Issue bodies in the business repository, but the fields apply under any configured platform adapter.

---

## Part 1: Canonical Task Template

**GitHub Issue title:** `[TASK-<number>] <Short Outcome-Oriented Title>`

```markdown
> This Task is generated by the configured Technical Agent from an approved, merged Business PR. It defines implementation approach and guidance. It is not `Technical Ready` until an Architect approves it.

## Metadata

| Field | Value |
| --- | --- |
| Task ID | `TASK-<number>` |
| Business Repository | `<this repository>` |
| Business PR | `<reference>` |
| Epic | `<reference>` |
| Source Story | `<STORY-id>` |
| Story Version | `<version>` |
| Target Application | `<application or product surface>` |
| Target Repository | `<engineering repository>` |
| Created By | `<Technical Agent run or author>` |
| Created At | `<timestamp>` |
| Status | `Draft` / `In Review` / `Rework Required` |
| Technical Readiness | `Not Ready` / `Ready for Architect Review` / `Technical Ready` / `Blocked` |
| Architect | `<name or Pending>` |
| Approval Reference | `<approval event or Pending>` |

## Acceptance Criteria

*(Preserved from the Source Story, unchanged in meaning.)*

```text
Given <starting condition>
When <user action or business event>
Then <observable product behavior>
```

## Implementation Approach

`<Guidance-level description of how the Story will be realized. Not code. Enough for a Developer Agent to begin.>`

## Technical Findings

`<What the Technical Agent found in the target repository relevant to this Task -- existing patterns, constraints, affected modules.>`

## Dependencies and Sequencing

| Depends On | Type | Notes |
| --- | --- | --- |
| `<Task/Spike ID or external item>` | Task / Spike / External | `<notes>` |

## Required Spikes

| Spike ID | Question | Status |
| --- | --- | --- |
| `SPIKE-<id>` | `<what must be resolved>` | Open / In Progress / Resolved |

## Architecture References

- `<link to architecture documentation in the target repository>`

## Testing and Quality Considerations

- `<what must be verified, at a guidance level>`

## Constraints

- `<technical constraint the Developer Agent must respect>`

## Unresolved Technical Risks

| Risk | Impact | Owner |
| --- | --- | --- |
| `<risk>` | `<impact>` | `<owner>` |

## Scope Conflicts (if any)

*(Only populate if technical analysis revealed the approved Story cannot be implemented as written -- see CANONICAL-TASK-SPEC.md section 8. Do not resolve here; escalate to the business-repository process.)*

- `<conflict, affected Story/Requirement, and escalation reference, or None>`

## Architect Review

| Field | Value |
| --- | --- |

## Part 2: Spike Template

**GitHub Issue title:** `[SPIKE-<number>] <Short Description of the Unknown>`

```markdown
> This Spike is an investigation, not implementation work. It resolves a technical unknown so that one or more blocked Tasks can be responsibly estimated and decomposed.

## Metadata

| Field | Value |
| --- | --- |
| Spike ID | `SPIKE-<number>` |

| Blocks | `<Task IDs>` |
| Owner | `<person or agent>` |
| Status | `Open` / `In Progress` / `Resolved` / `Abandoned` |
| Created At | `<timestamp>` |
| Resolved At | `<timestamp or Not Yet Resolved>` |

## Investigation Scope

`<What will be examined, and where.>`

## Expected Output

`<What this Spike must produce -- a decision, a recommendation, a feasibility answer.>`

## Findings

`<Recorded once resolved. Copied into the Technical Findings of every blocked Task.>`
```

## Part 3: Pre-Review Quality Gate (Technical Agent self-check)

```markdown
- [ ] Business PR is merged and Business Owner approval is recorded (CANONICAL-TASK-SPEC.md section 3)
- [ ] Source Story and Story Version are recorded and match the merged Business PR
- [ ] Acceptance Criteria are preserved unchanged from the Story
- [ ] Target Application and Target Repository are identified
- [ ] Implementation Approach is guidance-level, not code
- [ ] Every Required Spike is linked, not silently skipped
- [ ] Any Scope Conflict is recorded and escalated, not resolved unilaterally
- [ ] Status is Draft or In Review; Technical Readiness is not set to Technical Ready by the Technical Agent itself
```

## Summary

| File | Purpose |
| --- | --- |
| Canonical Task (Part 1) | Implementation approach, findings, dependencies, and the Architect gate for one decomposed unit of a Story |
| Spike (Part 2) | Investigation required before a blocked Task can be estimated |

The Technical Agent uses these as issue bodies for GitHub Issues in the business repository. The Architect reviews and completes the Architect Review section before Technical Readiness changes.
